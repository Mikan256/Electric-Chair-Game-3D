# 実装設計メモ

このドキュメントは `docs/denki_isu_game_rules.md` を Web ゲームとして実装する際の
解釈と、マルチプレイの設計判断をまとめたものです。

## 1. ルールの実装

| ルール | 実装 |
|---|---|
| 12 脚 | `config.chairCount = 12` |
| 交互に攻撃/防御 | 1 ターンごとに `attacker = otherPlayer(attacker)` |
| 攻撃側が 1 脚に電気を仕掛ける | `set` フェーズ。攻撃側だけが salted hash を送る |
| 防御側が 1 脚を選ぶ | `sit` フェーズ。守備側の椅子は公開される |
| 電流を流す | `press` フェーズ。攻撃側が前方台座のボタンを押す |
| 回避 | 防御側に「座った椅子番号」を加算 |
| 感電 | 防御側の累積ポイントを 0 に |
| 得点椅子 | `retiredChairs` に追加し、以後選択不可 |
| 感電椅子 | 何もせず、再使用可能 |
| 40pt 先取 | 回避加算直後に判定 |
| 3 回感電 | 攻撃側の `shocksDealt` が 3 で勝利 |
| 最大 8 ターン | 8 ターンの result 後に points 比較 |

### 「仕掛ける」と「ボタン」の区別

このゲームの隠された選択は **12脚のうちどの椅子に電流を仕掛けるか** です。
前方ステージの黒い台座の黄色いボタンは、その仕掛けを作動させるスイッチであり、
隠す対象そのものではありません。したがって画面では次を分けています。

- 攻撃側の仕掛け（椅子）: `press` まで相手に公開しない
- 守備側が座った椅子: `sit` 直後に公開
- 前方の黄色いボタン: 攻撃側が `press` で押す操作

### 明文化した追加仕様

- **ターン順**:
  1. 攻撃側が電気椅子を仕掛ける（秘密）
  2. 守備側が椅子に座る（公開）
  3. 攻撃側が前方のボタンを押す
  4. 判定・椅子の処理・攻守交代
- **着席の確定**: Web 版では守備側が「この椅子に座る」を押した時点で確定し、
  実写のような会話による変更は行わない（攻撃側のボタンとの競合を防ぐため）。
- **同点**: 8 ターン終了時にポイントが同じ場合は引き分け。
- **時間制限なし**: `set` / `sit` / `press` / `result` にフェーズ期限はなく、
  時間切れによる不戦敗もない。`result` はプレイヤーが「次へ」を押して進める。
- **降参/退出**: 相手の勝利（reason: `forfeit`）。
- **再戦**: 試合終了後に両者が `rematch` を押すと新しい matchId で開始。

## 2. 秘密の保護

攻撃側が仕掛けた椅子は、ホストを含む相手に `press` まで見せません。
攻撃側は先に salted hash を送り、守備側が座った後にボタンと同時に
椅子と salt を公開します。

```
chair, salt (128-bit) --hash--> commitment
set:   commitment のみ送信（攻撃側）
sit:   chair を公開（守備側）
press: chair + salt を送信（攻撃側）→ hash を検証して判定
```

- `commitmentHash(chair, salt)` は salt 依存の 53-bit ハッシュ。
  salt が 128-bit ランダムなので、12 候補の総当たりは不可能。
- 攻撃側は守備側の着席位置を見てから仕掛けを変更できない（hash 固定）。
- ホストは `wiredChair` を `MatchState` の内部に保持し、
  `MatchView` には `wiredCommitted` の真偽だけを出す。
- 守備側の `sittingChair` は実写同様に公開する。

## 3. 状態機械

```
set ──(攻撃側 commit)──▶ sit ──(守備側 chair)──▶ press ──(攻撃側 button)──▶ result
 ▲                                                                         │
 └──────────────────────────── advance ────────────────────────────────────┘
                                                                           │
                                                                      outcome あり
                                                                           ▼
                                                                       finished
```

- `MatchState` はイミュータブル。`applyAction()` が新しい state を返す。
- `revision` は単調増加。ネットワークのスナップショット連番とは別。
- フェーズ期限・タイムアウト処理は持たない。試合はプレイヤーの操作でのみ進む。
- `MatchView` は `you` ごとに生成。`wiredChair` は result まで含めない。

## 4. ネットワーク

```
[Game iframe A]                         [Game iframe B]
  FlaxiaClient (postMessage)              FlaxiaClient
  MatchSession (host)  ──sendPeerData──▶  MatchSession (guest)
        │                                      │
        └────────── 親フレームが中継 ──────────┘
```

- ホスト = `room.hostId` のプレイヤー。席順は `[host, guest]`。
- ゲストは `hello` を送り、ホストは最新ビューを返す。
- ホストは 2 秒ごとにハートビートとして最新ビューを再送（取りこぼし対策）。
- ビューは `seq` 付き。ゲストは `seq` の飛びを検知すると `sync` を送る。
- アクションは `turn` / `phase` 付き。古いアクションは STALE として破棄。
- `sendPeerData` の上限 65,536 bytes を超えないこと。
  現在のビューは履歴 8 件込みでも数 KB。

### 既知の制約

- ホスト交代（`MULTIPLAYER_HOST_CHANGED`）時の試合継続は未対応。
  新しいホストは旧ホストの秘密を持てないため、退出 = 降参として扱う。
- ルームの再接続・観戦・3 人以上は未対応。
- 親フレームの `MULTIPLAYER_ROOM_STATE` に `selfId` がない環境では、
  `PLAYER_IDENTITY` と「ゲーム開始を要求した側がホスト」の推定で自分を特定する。
  本番 SDK が `selfId` を返す場合はそれを優先する。

## 5. セットの再現

実物のセットに寄せるため、ステージは次の構成にしている。

- 12脚の**白い立方体**の椅子を時計回りに円形配置
- 座面は白い凸（RoundedBox）で、立方体の上に載せる
- 椅子の**外側面**に黒い数字（CanvasTexture）
- 椅子の**内側の床**に白い数字（放射状に配置）
- **部屋**: 床・奥壁・左右壁・照明トラス。奥壁中央に大型モニター
- **カメラ**: 完全 360° オービット。方位角は制限しないが、方位角ごとに
  部屋の内壁までの距離を計算して `maxDistance` を動的に下げ、カメラ位置も
  内壁の内側へクランプする。パンは無効、仰角は床と天井の内側に制限。
  待機中はゆっくり自動回転する。
- **前方ステージ**: 円形フロアの外側に、装飾のない黒い平たい台を 1 つ置く
- 台の**中心**に**黒い台座**と**黄色いボタン**を配置
- **奥壁モニター**: 22×11 の大型スクリーン。CanvasTexture に
  最新5ターンの経過表（攻撃側／着席椅子／電流椅子／判定／ポイント）を描画。
  現在ターンの電流椅子は `???` のまま表示し、未公開情報を漏らさない
- 椅子の外側面はキーライトだけでは暗くなるため、周囲に低いフィルライトを置く
- 時計画像の床テクスチャは使わず、椅子ごとの床数字で構成

## 6. 演出

- `result` 遷移時に、椅子のワイヤー（赤）と着席（緑/白）を 3D で表示。
- 感電: 閃光・雷ボルト・カメラシェイク・`se/electric.mp3`。
- 回避: 緑のバースト・`se/chair.mp3`。
- 3 回目の感電: `FINAL THUNDER` 動画 + ハートビート。
- 通常の感電: `lightning.mp4` を控えめに合成。
- 勝利: 紙吹雪 + `WINNER` オーバーレイ。
- BGM: タイトルは `MusMus-BGM-168.mp3`。ゲーム中は `Innovation.wav` を MP3 化してループ。
- ラウンド開始時: `ROUND N` の画面コールと音声（Piper TTS）、チャイム。

`ファイナルサンダー` は旧 Unity 実装では「仕掛けた後に押す演出ボタン」で、
ルール上の追加効果はない。本実装も演出のみ。
